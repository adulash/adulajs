# ADR 016: Business design skill, company identity and modal defaults

Status: accepted by the user on 2026-09-19; supplements the original v4 plan.

The kit's agent must use shadcn/ui components, apply a frontend-design skill suited to business systems, and present forms and row details in a shadcn Dialog unless the user requests another presentation. Company identity must be requested at project kickoff and applied from the first interface.

The package ships the self-contained `adula-frontend-design` skill. Managed AGENTS rules route all UI work to it. It prioritizes operational workflows, readable data density, consistent navigation and actions, validation, permissions, Arabic RTL, keyboard access and restrained use of the application's visual tokens. It does not assume access to a global skill installation. Semantic HTML remains valid for document structure and form submission; shadcn primitives supply visual controls.

The skill asks for missing company name, logo, colors, fonts and guidelines early, without repeating information already supplied. The agent records sources and unresolved choices in project-owned `docs/design-identity.md`. Pending identity permits independent work and provisional neutral previews, not invented or implicitly approved branding. Kit installation and upgrades never own or rewrite this file.

`adula:install` synchronizes both managed skills and their hashes; `adula:doctor` checks every expected skill against the installed package. Other project skills and text outside the managed AGENTS block stay project-owned.

The copied `ResourceSurface` composes shadcn Dialog, with a title, description, bounded scrolling, RTL, close control and Escape dismissal. `ResourcePage` uses it for form/show modes, including direct URLs. Closing returns to the resource list; the route-backed modal does not retain an underlying list or its filters. Clicking the backdrop does not discard the form. Custom resource overrides can use the same surface; the reference order form does. The explicit `presentation="page"` prop supports a user-requested alternative without changing server permissions or resource contracts. Lookup and organization controls in these forms compose shadcn Select.

Amendment (2.3.0): every long dialog, meaning one whose content can exceed the screen height, keeps its header (title and description) and its footer (actions) fixed while only the body scrolls, and that body shows its scrollbar at all times in light and dark themes. The registry's `long-dialog` (`LongDialogContent`) composes shadcn Dialog with the layout of `ResourceSurface`; the scrollbar uses CSS only (`overflow-y: scroll`, a stable gutter and theme-token colors), without a new scroll-area dependency. Platforms that force overlay scrollbars may still hide an idle thumb; the stable gutter keeps the scroll area recognisable there.

Amendment (2.3.0, owner's decision): record dialogs follow the same pattern. `ResourceSurface` renders `LongDialogContent`, and the record form and details place their actions in its fixed footer through `RecordFooter`, so saving, cancelling and the record actions stay on screen however long the record is. The footer follows the shared rule: secondary actions (record actions, print) at the start, then «إلغاء» (form) or «إغلاق» (details) as outline, then the primary action («حفظ السجل» or «تعديل السجل»). The form stays in the body; its save button names it with the `form` attribute, so Enter in a field, validation, the focus on the first invalid field (#118), the conflict alert and the unsaved-changes confirmation (#117) behave as before. On a record page (`presentation="page"`) `RecordFooter` renders the same actions in place. Bodies without `RecordFooter` (for example the invitation forms) keep their own buttons and get no empty footer.

Amendment (2.3.0, owner's decision): a dialog asks before closing only when there are unsaved changes. An untouched form, or one whose values were typed and changed back, closes at once on Escape, the close button, «إلغاء» or a click outside, whatever the dialog's `mode`. Every element that reports `data-dirty`, a form or any other element that edits values (such as a settings panel), is the reference for the controls inside it: `"false"` is clean whatever changed there. Every other control is compared with the value it had before the user changed it (recorded when the dialog content mounts, or when the control takes focus before a change), so a value changed and changed back is clean there too. The `confirmDialogClose` preference still turns the question off entirely.

Amendment (2.3.0, decision 23, owner: «ينبغى ان يكون سلوك عام وليس سلوك مخصص لكل نافذة»): clean close is the shared Dialog's behaviour alone, and no dialog computes its own dirty state. This replaces the `data-dirty` regions of the amendment above. A dialog whose state is plain inputs, text areas and selects declares nothing and the Dialog compares those controls as described above. Any other state is declared with the `value` prop of `Dialog` or with `useDialogValue(value)` from a component inside the dialog: the Dialog captures each declaration as it renders until the user first interacts with the dialog (pointer, key, input or change inside its content), so values reset on opening or loaded just after it are the starting point; on closing it compares the declarations with stable serialization (object keys sorted, files and dates as comparable data) and a restored value is clean. When a dialog declares state, its declarations are the whole truth for it and its controls are not compared one by one. A step saved within one opening, such as an uploaded file that becomes a mapping to review, starts a new baseline with `<DialogValue key={step} value={...} />`. The same holds for a save that keeps the dialog open (the mail settings stored while the password is refused): the key changes after the save, so the next close compares with what was saved. A dialog that declares a value declares its full form state, because its plain controls are then no longer compared; the Dialog warns on the console when a control changed while no declaration did, and the browser tests fail on that warning. No region owns an external editor today, so nothing reports `data-dirty`; `packages/ui/tests/dialog-clean-close.test.mjs` fails on any new `data-dirty` or hand-made JSON snapshot comparison outside its documented allowlist, which is empty, and the clean-close sweep (`tests/browser/clean_close_sweep.spec.ts`) opens and closes every reachable dialog without typing.

Amendment (2.3.0, decision 30): a dialog that creates, edits or shows a lasting item has its own address. It opens from a query parameter of the page it covers (`?new=1`, `?edit=<id>`, or named per dialog when a page has two), through the registry's `dialog-param` item (`useDialogParam`, and `useEntityDialog` for one create-and-edit dialog). Opening pushes the parameter with a client-side Inertia visit, so no request and no progress bar; Back closes the dialog and leaves the page mounted; a reload or a direct load opens it; closing goes Back when the page pushed the entry and otherwise replaces the parameter away. A value that names no item the user may open shows nothing and is removed with replace, so the address reveals nothing. An item outside the page props is fetched as before and opens once it arrives. Transient dialogs (confirmations, one-setting edits, reorder or customise, one-time secrets, step flows, logs and history) keep no address. `packages/ui/tests/dialog-urls.test.mjs` fails on a new dialog of the screens that is neither bound to the hook nor listed there as transient with its reason.

This establishes agent defaults and updates the generic resource consumer. It does not silently rewrite unrelated project-owned legacy screens or mark the broader phase 2 visual, performance or release gates complete.

Verification covers installed skill integrity and repair, company identity preservation, a packed independent consumer, and browser CRUD, nested controls, direct detail URLs, mobile bounds, keyboard focus, dismissal and the explicit page presentation. See the dated implementation-status entry for executed checks.
