# تثبيت AdulaJS

النسخة الإنجليزية: [Installing AdulaJS](../installation.md)

بعد أول تسجيل دخول افتح صفحة **الإعداد الأولي** لمراجعة هوية الشركة واختبار الإشعارات ووصول البريد والتخزين وخدمات التشغيل. راجع [الإعداد الأولي](initial-setup.md).

الإصدارات المنشورة مذكورة في [صفحة الإصدارات](../releases.md)، وكل إصدار منشور على وسم `latest` في npm.

## نظام جديد بأمر واحد

لكل شركة نظام واحد، وكل مجال عمل داخله (الأصول، الصيانة، الموارد البشرية...) تطبيق مستقل في المجلد `app/modules/<name>`. لإنشاء نظام جديد:

```sh
npm create adulajs my-system
```

الأمر `npx create-adulajs@latest my-system` يشغّل الحزمة نفسها مباشرة، أما `npm create adulajs` فيتبع [اصطلاح المُهيِّئات في npm](https://docs.npmjs.com/cli/v11/commands/npm-init/). لا يحتاج الأمر إلى مشروع AdonisJS موجود مسبقًا.

المتطلبات على الجهاز:

- Node.js الإصدار 24 أو أحدث، ومعه npm.
- في الوضع الافتراضي: Docker مثبّت ويعمل ومعه Compose. يشغّل المُنشئ PostgreSQL 17 وRedis 7 في حاويات محلية معزولة، بوحدات تخزين دائمة ومنافذ لا تُفتح إلا على الجهاز نفسه (loopback).
- بديلًا عن Docker يمكنك استخدام خدمات قائمة: `--services existing --connection /path/to/local.json`. راجع [خيارات المُنشئ](../../packages/create-adulajs/README.md).

ما يفعله المعالج بالترتيب تقريبًا:

1. يطلب هوية الشركة (الاسم مثلًا «شركة الريادة للمقاولات») وبريد المدير.
2. ينزّل pnpm والاعتماديات.
3. ينشئ قاعدتي بيانات جديدتين: واحدة للتطوير وأخرى للاختبار ينتهي اسمها بـ `_test`، ثم يطبّق الترحيلات (migrations).
4. يثبّت المهارات المُدارة لوكلاء البرمجة، ومكونات واجهة shadcn التي يملكها المشروع.
5. يهيّئ حساب المدير، ثم يشغّل الفحص (doctor) وفحص الأنواع ويبني ملفات الواجهة.

أين تذهب النتائج:

- بيانات دخول المدير في الملف `tmp/dev-admin.txt`، وهو مستبعد من Git.
- هوية الشركة في `docs/design-identity.md` الذي يملكه المشروع.
- سجل التثبيت المفصل في `tmp/install.log` (مستبعد من Git أيضًا).

لا يتضمن النظام الجديد أي تطبيقات تعليمية، ولا يستبدل المُنشئ ملفات أو قواعد بيانات موجودة بالاسم نفسه. على أنظمة Unix تُنشأ ملفات الأسرار بصلاحية القراءة لك وحدك (0600)؛ Windows يتجاهل هذه الصلاحية، فأبقِ المشروع داخل مجلد المستخدم الخاص بك، إذ تمنع صلاحياته الافتراضية المستخدمين الآخرين.

رسائل الطرفية بالإنجليزية، أما النظام نفسه فبالعربية. في الطرفيات التفاعلية تظهر الألوان ومؤشر تقدّم عبر ست مراحل، ومع `NO_COLOR=1` أو عند تحويل المخرجات إلى ملف تظهر أسطر نصية عادية.

### اختبار الأرشيفات محليًا

لتجربة المُنشئ قبل النشر، شغّل أولًا `pnpm test:create` في مستودع AdulaJS لينتج الأرشيفات الثلاثة الموثّقة، ثم شغّل المُنشئ بمساراتها المطلقة الفعلية:

```sh
npm exec --yes --package=/path/to/create-adulajs-<version>.tgz -- create-adulajs my-system --packages /path/to/archives
```

### التشغيل

داخل النظام المُنشأ شغّل `npm run dev`؛ يبدأ خادم HTTP وعامل الأحداث (worker) معًا. في بيئة الإنتاج يعمل العامل والمجدول (scheduler) عمليتين منفصلتين كما يشرح ملف README في النظام.

يثبّت المُنشئ اعتماديات المشروع والخدمات المحلية فقط. أما تثبيت Node وDocker، وخادم بريد حقيقي (SMTP)، وتسجيل الدخول عبر OAuth، وتخزين S3، والنسخ الاحتياطي خارج الموقع، واستضافة الإنتاج، فكلها إعدادات تتولاها أنت صراحة.

## متطلبات إضافة AdulaJS إلى مشروع AdonisJS قائم

- Node 24 أو أحدث، وpnpm 11.19.0.
- مشروع مبني على قالب AdonisJS 7 الرسمي مع React وInertia.
- PostgreSQL 17، مع إعداد Lucid على `pg`، والمصادقة (auth) والجلسات (session) والحماية (shield).

يرفض الأمر `configure adula` العمل إذا نقص أحد هذه المتطلبات أو كان الاتصال بغير PostgreSQL.

بيئة الواجهة المختبرة: React 19 وTailwind CSS 4.3.3 و`@tailwindcss/vite` 4.3.3 وshadcn 4.21.0. ثبّت مكونات السجل (registry) عبر أمر AdulaJS حتى يبقى تتبّع ملكية الملفات سليمًا.

## تجهيز الأرشيفات

في المستودع المصدري، يبني `pnpm test:consumer` الحزمتين ويحزمهما في `.work` ثم يتحقق منهما في مشروع مستقل. للتحزيم دون هذا الاختبار، ابنِ كل حزمة ثم شغّل `pnpm --filter adula pack --pack-destination <absolute-output-directory>` والأمر نفسه لـ `@adula/ui`. استخدم مسار إخراج مطلقًا موجودًا لتجنب الالتباس مع المسارات النسبية.

## إعداد مشروع AdonisJS قائم

داخل مشروعك ثبّت الأرشيفات بمساراتها الفعلية (المسارات والإصدار أدناه للتوضيح فقط):

```sh
pnpm add /path/to/adula-2.0.0.tgz /path/to/adula-ui-2.0.0.tgz
pnpm add tailwindcss@4.3.3
pnpm add -D shadcn@4.21.0 @tailwindcss/vite@4.3.3
node ace configure adula
node ace migration:run
```

يسجّل الإعداد المزوّدات (providers) والأوامر واكتشاف الترحيلات، وينسخ ملفات الخدمة والمتحكم والمسارات ومساعد اختبار HTTP التي يملكها مشروعك دون أن يكتب فوق تعديلاتك، ويضبط إضافات Japa للاختبارات المولَّدة.

ضع في `ADULA_ADMIN_EMAIL` بريد المدير المقصود (أو مرّر `--admin-email`)، ثم شغّل:

```sh
node ace adula:install --admin-name="مدير النظام"
node ace adula:doctor
```

### كيف يُنشأ حساب المدير

- **الحساب غير موجود ولا يوجد مدير بعد:** ينشئه `adula:install` بكلمة مرور عشوائية تُطبع مرة واحدة في الطرفية ولا تُكتب في أي ملف. سجّل الدخول وغيّرها.
- **الحساب موجود ولا يوجد مدير بعد** (مثلًا سجّل شخص ما بهذا البريد بنفسه): يعامله التثبيت حسابًا غير موثوق؛ يستبدل كلمة المرور بأخرى تُطبع مرة واحدة، وينهي جلسات الحساب ورموز API وروابط الاسترداد غير المستخدمة والدعوات المعلّقة، ويسجّل الحدث. لا تمرّر `--keep-password` إلا لحساب أنشأته أنت.
- **يوجد مدير بالفعل:** يُرفض أي بريد غير معروف بدل إنشاء حساب مميّز آخر.

### التسجيل الذاتي

التسجيل الذاتي ليس طريقة لإنشاء المدير الأول. عندما لا يُضبط `SIGNUP_ENABLED` يبقى التسجيل مفتوحًا حتى يوجد أول مدير، ثم يجيب بـ 404. اضبطه على `true` لإبقائه مفتوحًا، أو `false` لإغلاقه من البداية. يجيب التسجيل بالرد نفسه سواء كان البريد جديدًا أو مسجلًا أو مدعوًا، ولا يُدخل الزائر إلى النظام.

### خلف خادم وكيل

إذا كان النظام خلف خادم وكيل عكسي (reverse proxy)، اضبط `TRUSTED_PROXIES` على شبكة الوكيل (قيم مفصولة بفواصل: `loopback` أو `linklocal` أو `uniquelocal` أو عناوين أو نطاقات عناوين بصيغة التوجيه غير الصنفي (CIDR) مثل `10.0.0.0/8`)، حتى ترى أقفال الدخول وحدود الطلبات عنوان العميل الحقيقي. إن لم يُضبط فلا يُوثق إلا بعنوان الجهاز نفسه (loopback).

### ما يفعله التثبيت وما لا يفعله

يهيّئ التثبيت صلاحيات المدير الأساسية، ويزامن قواعد AGENTS والمهارات المُدارة، ويثبّت سجل مكونات الواجهة إذا كانت `@adula/ui` موجودة، مع حماية المكونات التي عدّلتها. لا يوفّر كل شاشات المصادقة والإدارة الموجودة في النظام المرجعي، ولا يربط كل محوّل اختياري تلقائيًا؛ هذا الربط مسؤولية مشروعك.

تكرار التثبيت يصلح أيضًا منحة `manage all` الأساسية إن فُقدت من دور مدير قائم، ويحافظ على باقي القواعد ومنها قواعد المنع الصريح. وتمنع الإدارة العادية إزالة آخر مدير نشط، وإزالة المدير صلاحياته هو. راجع [ADR 019](../decisions/019-admin-safety-and-calendar-preferences.md).

### صفحة الإعدادات

تتيح صفحة الإعدادات المولَّدة اختيار التقويم: الميلادي، أو الهجري (أم القرى)، أو كليهما. في وضع «كليهما» يظهر التاريخ المخزَّن الواحد بالتقويمين ويختار المستخدم تقويم الإدخال. وتتحكم الصفحة أيضًا في طلب تأكيد إغلاق نافذة التحرير وفي حركة الانتقال بين الصفحات، مع احترام إعداد «تقليل الحركة» في الجهاز. على المشاريع القائمة دمج الصفحات والوسائط (middleware) المحدّثة التي تملكها، ومراجعة تغييرات السجل عبر `adula:ui` قبل اعتماد هذه الإعدادات.

بعد النشر استبدل الأرشيفات **بالإصدار المنشور تحديدًا** لكل حزمة.

## أول مورد وأول تصميم

شغّل `node ace adula:resource inspections --module=inspections`، واملأ التسميات والحقول وبيانات الاختبار المولَّدة (الحقول تحدد التحقق والأعمدة؛ راجع [تعريف الموارد](resources.md))، ثم طبّق الترحيل وشغّل الاختبارات. لا يثبّت AdulaJS تطبيقات العملاء أو الطلبات أو المهام؛ أمثلة المستودع للاختبار فقط.

في بداية المشروع يطلب وكيل التصميم اسم الشركة وشعارها وألوانها المعتمدة وخطوطها ودليل هويتها، ويعيد استخدام ما يُعطى، ويسجّل مصادره في `docs/design-identity.md` الذي يملكه المشروع. إن تأخرت هذه المواد يستمر العمل بمعاينة محايدة مؤقتة. لا يكتب التثبيت فوق هذا الملف أبدًا.

أعمال الواجهة تتبع `.agents/skills/adula-frontend-design/SKILL.md` ومكونات shadcn المحلية، وتُعرض النماذج وتفاصيل السجلات في نافذة حوار (Dialog) افتراضيًا، إلا إذا طلب المستخدم صراحة صفحة كاملة. لمعاينة تحديثات المكونات شغّل `node ace adula:ui add all --preview` وراجع الملفات المعدّلة قبل الدمج.

## معنى «التثبيت بأمر واحد»

- `npm create adulajs my-system` ينشئ نظامًا كاملًا ويهيّئه من مجلد فارغ.
- `node ace adula:install` يهيّئ AdulaJS داخل مشروع AdonisJS قائم.
- الأمر `make deploy` في الخطة ينشر النظام على الخادم، وليس أداة تثبيت عبر npm.
