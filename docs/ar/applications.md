# التطبيقات داخل النظام

النسخة الإنجليزية: [Applications in a system](../applications.md)

تشغّل الشركة نسخة واحدة من AdulaJS هي **النظام**. وكل مجال عمل داخله، مثل الأصول أو الصيانة أو الموارد البشرية، هو **تطبيق**. التطبيق وحدة (module) في المجلد `app/modules/<name>`، ومسجّلة في `start/modules.ts`.

لا تنشر نظامًا منفصلًا لكل مجال عمل: تطبيقات النظام الواحد تتشارك البيانات والأشخاص. مثال: في نظام «شركة الريادة للمقاولات» يكون «طلبات الإجازة» و«الصيانة» تطبيقين في النظام نفسه، فيدخل الموظف مرة واحدة ويرى مهام التطبيقين في صندوق واحد.

## ما يتشاركه التطبيق مع غيره

كل تطبيقات النظام تستخدم:

- **المستخدمين وتسجيل الدخول نفسه:** حساب واحد لكل شخص، ودخول واحد، وجلسة واحدة للنظام كله.
- **الأدوار:** يأتي التطبيق بأدوار افتراضية، ويسندها المدير من شاشة الأدوار نفسها التي فيها بقية الأدوار، ويمكن للشخص أن يحمل أدوارًا من عدة تطبيقات.
- **الهيكل التنظيمي:** الموارد المقيّدة بالنطاق تنتمي إلى وحدة تنظيمية، فتحدد الإدارات والفروع ما يراه كل شخص في كل التطبيقات.
- **الإشعارات وصندوق المهام:** الإسنادات وموافقات سير العمل والإشارات (mentions) من كل التطبيقات تصل إلى صندوق واحد («مهامي») وقائمة إشعارات واحدة.
- **القوائم المرجعية والتسلسلات:** قيم القوائم المرجعية (lookups) وتسلسلات الترقيم تُدار من شاشتي الإدارة `/admin/lookups` و`/admin/sequences`.
- **سجل التدقيق:** كل تغيير يُسجَّل في سجل النشاط نفسه.

## إضافة تطبيق

```bash
node ace adula:app leave_requests --label-ar="طلبات الإجازة" --label-en="Leave requests"
```

| الخيار | المعنى |
| --- | --- |
| `<name>` | الاسم المختصر: حروف إنجليزية صغيرة وأرقام و`_`، يبدأ بحرف، وطوله 40 حرفًا على الأكثر. تُرفض أسماء الإطار المحجوزة (`admin` و`users` و`roles` و`lookups`...) وأسماء التطبيقات الموجودة. |
| `--label-ar` | التسمية العربية، وهي مطلوبة؛ تصبح اسم مجموعة التطبيق في القائمة. |
| `--label-en` | التسمية الإنجليزية، اختيارية؛ الافتراضي هو الاسم بعد استبدال `_` بمسافة وتكبير أول حرف (`Leave requests`). |
| `--dry-run` | يطبع كل مجلد وملف سيُنشأ والتعديل على `start/modules.ts` دون أن يكتب شيئًا. |

ينشئ الأمر:

- الملف `app/modules/<name>/module.ts`: التسميات، و`dependsOn: []`، والمورد المثال، ودورين افتراضيين:
  - `<name>_manager`: عرض وإنشاء وتعديل وحذف.
  - `<name>_user`: عرض وإنشاء، وتعديل السجلات التي أنشأها المستخدم نفسه فقط.
- موردًا مثالًا يحمل اسم التطبيق، يُولَّد كما يولّده `adula:resource`: التعريف، وترحيل الإنشاء، واختبار عقد الأمان الخاص به. التحقق والأعمدة والنماذج كلها مشتقة من التعريف؛ لا يُكتب مدقّق (validator) ولا نموذج (model) ولا مصنع بيانات (factory).
- مجلدات الوحدة الفارغة (`models` و`resources` و`validators` و`migrations` و`workflows`...).
- اختبار سريع (smoke test) `tests/functional/<name>/smoke.spec.ts` يفتح قائمة المورد بصفته مديرًا ويتحقق من مجموعة التطبيق في القائمة.
- تسجيل التطبيق في `start/modules.ts` بعد العلامة `/* adula:modules */`.

بعد ذلك:

1. شغّل `node ace migration:run`.
2. املأ المورد المثال (الحقول والقائمة والنموذج؛ راجع [تعريف الموارد](resources.md))، ثم شغّل `node ace adula:resource:migration <name>` و`node ace migration:run` مرة أخرى لإضافة الأعمدة الجديدة. حدّث بيانات اختبار العقد في `tests/functional/<name>.spec.ts`.
3. شغّل `node ace adula:install`؛ ينشئ الأدوار الافتراضية وقيم القوائم المرجعية الناقصة. ولا يغيّر أبدًا دورًا أو قيمة موجودة، فبعد التثبيت يملكها المديرون.
4. أسند الأدوار للأشخاص من `/admin/users`، ثم شغّل الاختبارات.

لإضافة موارد أخرى إلى التطبيق: `node ace adula:resource <resource> --module=<name>`.

## التكامل مع برامج الشركة الأخرى

يتواصل النظام مع الخارج عبر قنوات مشتركة ومدقَّقة، لا عبر الوصول المباشر إلى قاعدة البيانات:

- **واجهة برمجة التطبيقات (API):** المسار `/api/v1` يتيح عمليات الموارد بصلاحيات صاحب الرمز الحالية. ينشئ كل شخص رموز API من قائمة حسابه، ويصف `/api/v1/openapi.json` ما يحق للمستدعي استخدامه. راجع [API tokens and OpenAPI](../business-features.md#api-tokens-and-openapi).
- **الإشعارات الآلية الصادرة (outgoing webhooks):** إرسال موقَّع لأحداث العمل إلى عناوين HTTPS مشتركة. راجع [Outgoing webhooks](../business-features.md#outgoing-webhooks).
- **الإشعارات الآلية الواردة (inbound webhooks):** أحداث موقَّعة من برامج أخرى، تُطلق باسم `inbound.<key>.<event>` وتعالجها مستمعات التطبيق التي لا يضرها التكرار. راجع [Inbound webhooks](../business-features.md#inbound-webhooks).
- **الاستيراد:** استيراد ملفات CSV إلى أي مورد، مع التحقق نفسه الذي يطبّقه النموذج. راجع [CSV import](../business-features.md#csv-import).

## مثال كامل: طلبات الإجازة

لبناء هذا التطبيق بنفسك خطوة بخطوة، مع سير عمل الموافقة والتفويض ولوحة المؤشرات، اتبع [الدرس التطبيقي: طلبات الإجازة](tutorial-leave-requests.md).

بيانات الاختبار `apps/reference/tests/fixtures/modules/leave_requests` أُنشئت بالأمر أعلاه ثم مُلئت. وبحسب [ADR 017](../decisions/017-test-only-examples-and-release-gates.md) فهي للاختبار فقط: تُسجَّل عبر `tests/fixtures/modules.ts`، ولا تظهر أبدًا في قائمة النظام المرجعي العادية.

ما أُضيف بعد التوليد:

- حقول المورد: الموظف (مستخدم)، وتاريخا البداية والنهاية، والسبب، والحالة من قائمة مرجعية.
- قائمة مرجعية يعلنها التطبيق ويزرعها `adula:install`:

  ```ts
  lookups: {
    leave_request_status: [
      { key: 'pending', label: { ar: 'قيد المراجعة', en: 'Pending' } },
      { key: 'approved', label: { ar: 'معتمد', en: 'Approved' } },
      { key: 'rejected', label: { ar: 'مرفوض', en: 'Rejected' } },
    ],
  },
  ```

يتحقق الاختبار `apps/reference/tests/functional/leave_requests_app.spec.ts` من النتيجة كاملة على PostgreSQL:

- بعد الزرع يرى المدير الدورين `leave_requests_manager` و`leave_requests_user` بقواعدهما في شاشة الأدوار، وتكرار الزرع لا يغيّر شيئًا.
- قائمة المدير فيها مجموعة «طلبات الإجازة».
- صاحب دور `leave_requests_user` يعرض الطلبات وينشئها ويعدّل طلباته هو، لكنه لا يستطيع تعديل طلب شخص آخر ولا حذف أي طلب؛ أما المدير فيستطيع.

أما الأمر نفسه فيغطيه الاختبار `packages/adula/tests/app_command.spec.ts`، الذي يشغّل `node ace adula:app` في نسخة مؤقتة من النظام المرجعي ويفحص أنواع النتيجة.
