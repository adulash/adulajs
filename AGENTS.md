# AdulaJS development

Read adulajs-plan.md, docs/decisions, docs/implementation-status.md and GAPS.md before extending the framework. This is AdulaJS's source repository; changing packages/adula is expected here. Applications consuming the published package must not change its installed internals.

Use English for code/docs and Arabic for user-facing text. Keep migrations additive and immutable after release. Every feature needs a consumer and a meaningful test. Do not claim a phase complete before its acceptance gate passes. Never substitute mock authorization or SQLite for PostgreSQL authorization tests.

For UI work, use the frontend-design skill and read packages/adula/agent/skills/adula-frontend-design/SKILL.md. Design for business workflows and consistent data-dense interfaces. At project kickoff request any missing company identity (name, logo, colors, fonts and brand guide) before the first design; reuse supplied identity and record it in project-owned docs/design-identity.md. Compose project-owned shadcn/ui components instead of hand-styled native controls. All forms and row/record detail views use shadcn Dialog by default unless the user explicitly requests another presentation; semantic HTML for structure and submission is allowed. Preserve project-owned customizations and install consumer components through adula:ui.

Validation: pnpm build, pnpm typecheck, pnpm test, pnpm lint, pnpm check:boundaries. PostgreSQL 17 must be running. Tests use a dedicated *_test database. Never weaken or remove tests to hide a failure.

The user authorized the dependencies named in the implementation plan. Preserve project-owned UI and managed AGENTS boundaries. External deployment/publication requires actual destination configuration; do not invent accounts, domains or credentials.

Customers/orders/tasks were removed from normal application operation by the owner. Keep their acceptance consumers under apps/reference/tests/fixtures and never re-enable them in the normal registry or menu. See ADR 017. Releases follow docs/releasing.md (ADR 040): a v<version> tag on main, CI on that commit and the owner's approval of the npm environment; CHANGELOG.md is the only chronology. Before preparing archives, also run pnpm test:release, pnpm test:consumer and pnpm check:release --artifacts=.work.

Branches and issues: name every branch `<type>/<issue>-<slug>` (for example `feat/42-workflow-decision-steps`, or `chore/<slug>` without an issue) so the name states what it changes. When a session assigns a generated name, create the descriptive branch and push there instead; this rule is the owner's standing permission. Delete merged branches only after the final release. AdulaJS issues use the forms in .github/ISSUE_TEMPLATE (gap or bug) and describe AdulaJS, reproduced on a new application from create-app, never a consumer project; the Issue template workflow labels others `needs-template`. Triage decides scope: an issue that serves AdulaJS is fixed and closed by its PR; one outside AdulaJS's scope is closed as not planned with the reason in one comment.
